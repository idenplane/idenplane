# Custom Auth Flows

An authentication flow is an ordered list of steps stored on an `AuthenticationFlow` record. Each step has a type (`password`, `totp`, `webauthn`, ...), whether it's required, a position in the sequence, an optional condition that decides whether the step applies, and an optional fallback step to run if it fails. Flows are created and edited per realm, through the Admin API or the visual flow editor in the admin console, and are **bound** explicitly: to the realm as its browser flow, or to individual clients as overrides.

:::note Off by default
The login runtime is opt-in at every level: the server switch `AUTH_FLOW_RUNTIME_ENABLED=true`, the realm's `authFlowsEnabled`, and an explicit binding. Without all three, every sign-in uses the built-in login, whatever is bound. See [Running Flows at Login](#running-flows-at-login).
:::

---

## The Flow Model

A flow is a `name`, an optional `description`, a `version`, and an ordered array of steps:

```typescript
interface FlowStep {
  id: string;                       // unique within the flow, max 100 characters
  type: 'password' | 'ldap' | 'totp' | 'webauthn';
  required: boolean;
  order: number;                    // integer >= 1, unique; lower runs first
  condition?: {
    field: string;                  // one of the whitelisted fields below
    operator: 'eq' | 'neq' | 'in' | 'not_in' | 'exists' | 'not_exists';
    value?: unknown;
  } | null;
  fallbackStepId?: string | null;   // step to run instead if this one fails
  config?: Record<string, unknown>; // step-type-specific settings
}
```

`version` starts at 1 and the server increments it on every update.

`isDefault` still exists on flows but is **deprecated**: it is informational only and is never used to decide which flow a login runs. Bind flows explicitly (see [Binding Flows](#binding-flows)).

### Step Types

| Type | Identifies the user | Config keys |
|---|---|---|
| `password` | Yes | none |
| `ldap` | Yes | `federationProviderId` (string) |
| `webauthn` | Yes (passwordless) or second factor | `rpName` (string), `userVerification` (`required`, `preferred`, `discouraged`) |
| `totp` | No (second factor) | `issuer` (string), `digits` (`6` or `8`), `algorithm` (`SHA1`, `SHA256`, `SHA512`) |

`social`, `email_otp`, `magic_link` and `consent` are recognised but **not supported yet**: a flow that uses them is rejected with `unsupported_type`. Social, email OTP and magic-link steps are planned for a later release; consent is not a flow step (it is handled after the flow, as today).

### Conditions

A condition gates whether a step applies. `field` must be one of:

`user.username`, `user.email`, `user.emailVerified`, `user.groups`, `user.roles`, `user.totpEnrolled`, `user.webauthnEnrolled`, `client.clientId`, `risk.level`

`eq`/`neq` take a string, number or boolean; `in`/`not_in` take a non-empty array (at most 100) of those; `exists`/`not_exists` take no value. The first step may not have a condition.

### Fallbacks and the Execution Model

The validation rules below assume this model, and the runtime follows it:

- The **main path** is every step that is not the fallback target of another step, run in ascending `order`. The first step (lowest `order`) always starts the flow.
- A **fallback step** (the target of some `fallbackStepId`) is an alternative: it runs only when the step that names it fails, never by advancing along the main path.
- The **identification phase** is the first step plus every step reachable from it through fallbacks. These are the identifying steps.

### Validation

Every create and update runs the same strict validator; a failing flow is rejected with `400` and the full list of problems:

```json
{
  "statusCode": 400,
  "message": "Authentication flow is invalid",
  "errors": [
    { "path": "steps[0].type", "code": "first_step_not_identifying", "message": "The first step must identify the user (password, ldap, webauthn); 'totp' does not" }
  ]
}
```

The rules:

- 1 to 20 steps; step `id`s unique and non-empty; `order`s unique integers ≥ 1.
- Supported step types only (see above).
- The first step identifies the user (`password`, `ldap` or `webauthn`), is required, and has no condition.
- Every `fallbackStepId` points at another existing step of the flow, not at the first step; the fallback graph has no cycles; and no step is unreachable.
- Identifying steps may only fall back to identifying steps.
- Conditions use only the whitelisted fields, a known operator, and a value of the right shape.
- Each step's `config` contains only the keys listed for its type, with valid values.

Flows saved before these rules may not pass them. `POST …/auth-flows/{id}/validate` checks a stored flow without changing it, and a flow that fails validation cannot be bound.

## Binding Flows

Bindings are explicit and opt-in at every level:

| Setting | Where | Meaning |
|---|---|---|
| `AUTH_FLOW_RUNTIME_ENABLED` | server environment | Operator switch. Unset (or anything but `true`): every realm uses the built-in login. |
| `authFlowsEnabled` | realm | Per-realm switch, off by default. Off: built-in login, even with flows bound. |
| `browserFlowId` | realm | The realm's browser flow. |
| `authFlowId` | client | Per-client override of the realm's browser flow. |

A login resolves its flow in this order:

1. `AUTH_FLOW_RUNTIME_ENABLED` unset → built-in login.
2. The realm's `authFlowsEnabled` is off → built-in login.
3. Take the client's `authFlowId`, else the realm's `browserFlowId`. Neither set → built-in login.
4. Load that flow from the same realm and validate it. If it is missing or invalid, the login **fails closed** with an error page. It never falls back to the built-in login, to an `isDefault` flow, or to another flow.

A bound flow must belong to the same realm as the realm or client it is bound to; the server checks this on every write. A flow that is bound to the realm or to any client cannot be deleted: `DELETE` returns `409` with the list of bindings, so unbind it first.

### Bindings API

```bash
curl http://localhost:3000/admin/realms/my-realm/auth-flows/bindings \
  -H "x-admin-api-key: $ADMIN_API_KEY"
```

```json
{
  "runtimeEnabled": false,
  "authFlowsEnabled": false,
  "browserFlowId": null,
  "clients": [
    { "id": "6f1c…", "clientId": "my-web-app", "name": "Web App", "authFlowId": null }
  ]
}
```

`runtimeEnabled` reports the server's `AUTH_FLOW_RUNTIME_ENABLED` and is read-only.

`PUT` takes the same fields and updates only the ones you send. `clients` patches only the listed clients, identified by their OAuth `client_id`; send `"authFlowId": null` to remove an override.

```bash
curl -X PUT http://localhost:3000/admin/realms/my-realm/auth-flows/bindings \
  -H "x-admin-api-key: $ADMIN_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "browserFlowId": "{flowId}",
    "authFlowsEnabled": true,
    "clients": [{ "clientId": "my-web-app", "authFlowId": "{otherFlowId}" }]
  }'
```

Every flow the request binds must exist in the realm and pass validation. When the result has `authFlowsEnabled: true`, every binding that would then be in effect is checked, including client overrides not in the request. Otherwise the request is rejected with `400` and nothing is written:

```json
{
  "statusCode": 400,
  "message": "Flow binding rejected",
  "errors": [
    { "path": "clients[0].authFlowId", "code": "flow_invalid", "flowId": "…", "message": "Flow 'Legacy' is invalid: …", "flowErrors": [ … ] }
  ]
}
```

Other binding error codes: `flow_not_found`, `client_not_found`, `client_duplicate` and `flow_id_required`.

### Assigning One Client

`PUT …/auth-flows/{flowId}/assign-client/{clientId}` binds the flow in the path to one client. Here `{clientId}` is the client's primary key (`id`), not its OAuth `client_id`. The request:

- returns `404` if the flow or the client is not in the realm;
- returns `400` if the body names a different `authFlowId`, or if the flow fails validation.

To remove the assignment, send `DELETE` to the same path.

### Default Flows

`POST .../auth-flows/seed-defaults` seeds three built-in flows for a realm, skipping any that already exist by name. All three pass validation. Seeding binds nothing.

| Name | Steps |
|---|---|
| Simple Login | `password` |
| MFA Required | `password` → `totp` |
| Passwordless | `webauthn` |

## Running Flows at Login

### Enabling the runtime

1. Start the server with `AUTH_FLOW_RUNTIME_ENABLED=true`. Only the exact value `true` (any case) turns it on.
2. Bind a flow to the realm (`browserFlowId`) and/or to clients (`authFlowId`).
3. Turn on the realm's `authFlowsEnabled`. The bindings API checks every binding that would take effect before it accepts the switch.

```bash
curl -X PUT http://localhost:3000/admin/realms/my-realm/auth-flows/bindings   -H "x-admin-api-key: $ADMIN_API_KEY"   -H "Content-Type: application/json"   -d '{ "browserFlowId": "{flowId}", "authFlowsEnabled": true }'
```

To switch back to the built-in login, turn `authFlowsEnabled` off for the realm, or unset `AUTH_FLOW_RUNTIME_ENABLED` for the whole server. A login already in progress may have to be started again from the application.

### How a login runs

The flow drives the same hosted pages and endpoints as the built-in login, so themes keep working:

| Step type | Page | Endpoint |
|---|---|---|
| `password`, `ldap` | login page | `POST /realms/{realm}/login` |
| `totp` | second-factor page (authenticator, texted or recovery code) | `POST /realms/{realm}/totp` |
| `webauthn` | login page, *Sign in with a passkey* | `POST /realms/{realm}/webauthn/authenticate/verify` |

- **A server-side login transaction.** `/auth` validates the request, starts a transaction and points the browser at it with the `IDENPLANE_AUTHN_TXN` cookie. The transaction lasts 10 minutes. It pins the flow's id and `version`, holds the OAuth request, the identified user, the current step and a receipt for each step passed. OAuth parameters posted in forms are ignored. The cookie value changes once the user is identified.
- **Steps.** A step passes, or it fails and its fallback runs, or, with no fallback, the page shows an error. After five failed answers the login starts over. A locked account, a rate-limited second factor or an unexpected error ends the login; it never moves to the fallback.
- **Declining a step.** Submitting to the endpoint of the current step's own, direct fallback (for example, the password form while a passkey step with a password fallback is current) counts as failing the current step, so the fallback runs. Any other endpoint is refused (see below).
- **Conditions and `required`.** A step whose condition is false is skipped. A step without a condition applies; if the user has no credential for it (no authenticator app, no passkey), an optional step is skipped and a required one runs its fallback. A required `totp` step makes a user without a second factor enrol one first, as a realm that requires MFA does.
- **Checks after identification.** Once the user is identified, the same checks as the built-in login run once: risk assessment (a block ends the login), email verification, and password expiry (not after a passkey).
- **Never weaker than the built-in login.** The session's `acr` and `amr` come only from the steps actually passed. The login must reach the strongest of: the requested `acr_values` or `claims` acr, the client's required ACR, the risk level, and MFA when the client or realm requires it or the user has a second factor. If the flow fell short, the runtime adds a second-factor or passkey step the user can do, or sends a user without a second factor through MFA enrolment. A client's required ACR that the user cannot reach ends in `access_denied`.
- **After the flow.** The transaction is claimed once, the SSO session is created, and consent and the authorization code follow as for every sign-in. Consent is not a flow step.

### Single sign-on

An existing SSO session serves a client bound to a flow only if it is at least as strong as the flow requires **of that session's user**. At `/auth` the flow's conditions are evaluated for the user, with the same fields as at login (groups, roles, enrolled authenticator app or passkey, `client.clientId`), and the requirement is the weakest way through the steps that apply:

- A required step counts when its condition holds (or it has none). An optional step counts when the user has the credential for it, since it would run at login.
- A condition on a field that is only known during a login (`risk.level`) counts as holding, so the user signs in again rather than skipping the step.

A weaker session signs in again through the flow; with `prompt=none` the response is `interaction_required`. For example, with *password, then TOTP for group `G`*, a password-level session serves a user outside `G` silently, while a member of `G` signs in again and passes the TOTP step.

### Failing closed

- A binding to a missing or invalid flow shows a `503` error page at `/auth` and on the login page. It never falls back to the built-in login.
- A login that has to start again (expired, flow changed or unbound, a lockout, an error, another user, too many failures) goes back through `/auth` with the original authorization request, so the binding, single sign-on and `prompt` apply again; the login page then says why. A sign-in to the account console, which has no authorization request, starts again at the login page.
- A submission for another step than the current one is refused with `400`, and the transaction ends.
- A step after identification cannot switch user: another account's password or passkey ends the transaction.
- Of two concurrent submissions of the same step, the second is refused with `409`. A finished transaction cannot be replayed.
- Where a login is bound, the built-in sign-in paths cannot create a session: a stale login form starts again, and a social (identity-provider) sign-in is refused with a themed `403` page as soon as it returns from the provider, before any second factor is asked for (social steps are not supported yet).

### Current limits

- On a passkey step without a password fallback, the built-in themes hide the password form (the template gets `passkeyOnly`). A custom theme that does not check `passkeyOnly` still shows it, and submitting it there ends the transaction.
- Identity-provider buttons are hidden on bound logins.

## Admin API

Base path: `/admin/realms/{realm}/auth-flows`, protected by the admin API key. `{realm}` accepts either the realm's UUID or its name. Every write is recorded as an admin event (resource type `AUTH_FLOW`) when the realm has admin events enabled.

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/admin/realms/{realm}/auth-flows` | Create a flow (validated) |
| `GET` | `/admin/realms/{realm}/auth-flows` | List flows |
| `GET` | `/admin/realms/{realm}/auth-flows/bindings` | Get the realm's bindings |
| `PUT` | `/admin/realms/{realm}/auth-flows/bindings` | Update the realm's bindings (validated) |
| `GET` | `/admin/realms/{realm}/auth-flows/{id}` | Get one flow |
| `POST` | `/admin/realms/{realm}/auth-flows/{id}/validate` | Validate a stored flow: `{ valid, errors }` |
| `PUT` | `/admin/realms/{realm}/auth-flows/{id}` | Update a flow (validated; increments `version`) |
| `DELETE` | `/admin/realms/{realm}/auth-flows/{id}` | Delete a flow (`409` with `bindings` while bound) |
| `PUT` | `/admin/realms/{realm}/auth-flows/{id}/assign-client/{clientId}` | Bind the flow to one client |
| `DELETE` | `/admin/realms/{realm}/auth-flows/{id}/assign-client/{clientId}` | Remove that client's binding |
| `POST` | `/admin/realms/{realm}/auth-flows/seed-defaults` | Seed the three built-in flows |

### Create a Flow

```bash
curl -X POST http://localhost:3000/admin/realms/my-realm/auth-flows \
  -H "x-admin-api-key: $ADMIN_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "MFA with WebAuthn Fallback",
    "description": "Password + TOTP, falling back to WebAuthn if TOTP fails",
    "steps": [
      {
        "id": "step-password",
        "type": "password",
        "required": true,
        "order": 1
      },
      {
        "id": "step-totp",
        "type": "totp",
        "required": true,
        "order": 2,
        "condition": {
          "field": "user.groups",
          "operator": "in",
          "value": ["employees", "contractors"]
        },
        "fallbackStepId": "step-webauthn"
      },
      {
        "id": "step-webauthn",
        "type": "webauthn",
        "required": false,
        "order": 3
      }
    ]
  }'
```

Here `step-webauthn` is a fallback step. It runs only when `step-totp` fails, not after `step-totp` succeeds.

## Admin Console

**Auth Flows**, under the realm's *Sign-in behaviour* section, lists the realm's flows under a **Flow bindings** panel.

The **Flow bindings** panel has:

- the realm browser flow;
- the *Use custom flows in this realm* switch;
- a per-client override for each client.

While the server runs without `AUTH_FLOW_RUNTIME_ENABLED`, the panel shows a note that login ignores the bindings. Validation errors from the server appear next to the field they concern.

Opening a flow opens a canvas-based editor:

- **Step palette.** Drag a step onto the canvas, or click it to append it. Types the runtime does not support yet are marked *coming*.
- **Fallback connections.** These render as dashed lines between steps.
- **Preview mode.** Walks the flow top to bottom.
- **Validation errors on save.** Errors are listed per step.

The editor's client-side warnings are advisory. The server-side validation above is what's enforced.
