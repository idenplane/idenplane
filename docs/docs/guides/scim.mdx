# SCIM 2.0 Provisioning

Idenplane implements the SCIM 2.0 protocol (RFC 7644) so an external identity provider — Okta, Azure AD (Entra ID), or anything else that speaks SCIM — can create, update, and deprovision users and groups directly, instead of you syncing them by hand.

---

## Concepts

### Base URL and Endpoints

The SCIM base path for a realm is:

```
/scim/v2/{realmName}
```

where `{realmName}` is the realm's `name` (not its UUID). The implemented resource endpoints, all under that base path:

| Method | Path | Purpose |
|---|---|---|
| `GET` / `POST` | `/Users` | List (with filter/pagination) / create |
| `GET` / `PUT` / `PATCH` / `DELETE` | `/Users/{id}` | Get / full replace / partial update / deprovision |
| `POST` | `/Users/.search` | Search via POST body instead of query string |
| `GET` / `POST` | `/Groups` | List (with filter/pagination) / create |
| `GET` / `PUT` / `PATCH` / `DELETE` | `/Groups/{id}` | Get / full replace / partial update / delete |
| `POST` | `/Groups/.search` | Search via POST body |
| `POST` | `/Bulk` | Batch of the operations above in one request |

The discovery endpoints need **no authentication** and are served both at `/scim/v2` and under each realm's base URL, where SCIM clients look for them: `GET /ServiceProviderConfig`, `GET /Schemas` (and `/Schemas/{id}`), and `GET /ResourceTypes` (and `/ResourceTypes/{name}`). `/Schemas` and `/ResourceTypes` answer with a `ListResponse`, as RFC 7644 §4 requires.

Requests may be sent as `application/scim+json` (what Entra ID, Okta and OneLogin send, per RFC 7644 §3.1) or `application/json`. Responses are `application/scim+json`.

### Authentication

Every `/Users`, `/Groups`, and `/Bulk` call requires `Authorization: Bearer <token>`. The token is opaque — generated by Idenplane, not a JWT — and validated by hashing the presented value with SHA-256 and comparing it against the stored hash; the plaintext is never stored and is shown to you exactly once, at creation time.

If the realm's SCIM provisioning is turned off, or the bearer token is missing, unknown, revoked, expired, disabled, or issued for a different realm, every one of those endpoints returns **401 Unauthorized** (not 403 — despite what the admin console's toggle description says).

Tokens carry `scopes` (defaulting to `["urn:scim:schemas:core:1.0:Users", "urn:scim:schemas:core:1.0:Groups"]` if you don't specify any) and an optional `expiresAt`. As of today, `scopes` are stored and returned but not read anywhere in the authorization check — they're a label for your own bookkeeping, not an access-control boundary. Every valid token can call every SCIM endpoint in its realm regardless of its `scopes` value.

### Schema URNs and Errors

Resources and messages use the RFC 7643/7644 **2.0** URNs: `urn:ietf:params:scim:schemas:core:2.0:User` and `:Group`, the enterprise extension `urn:ietf:params:scim:schemas:extension:enterprise:2.0:User`, and `urn:ietf:params:scim:api:messages:2.0:ListResponse`, `:Error`, `:PatchOp`, `:BulkRequest` and `:BulkResponse`. `meta.location` is the resource's absolute URL under the realm's base URL (built from `BASE_URL`), and a create also returns it in the `Location` header.

Errors use the RFC 7644 §3.12 body:

```json
{
  "schemas": ["urn:ietf:params:scim:api:messages:2.0:Error"],
  "status": "409",
  "scimType": "uniqueness",
  "detail": "User 'jsmith' already exists"
}
```

`scimType` is set where RFC 7644 defines one: `uniqueness` (409: userName, email or group name taken), `invalidFilter`, `invalidPath`, `noTarget`, `invalidValue`, `invalidSyntax`, `mutability` (400) and `tooMany` (413, Bulk).

### User and Group Field Mapping

| SCIM attribute | Idenplane field | Notes |
|---|---|---|
| `userName` | `username` | Required; must be unique in the realm |
| `name.givenName` | `firstName` | |
| `name.familyName` | `lastName` | |
| `emails` (primary, or first if none marked primary) | `email` | Must be unique in the realm. Returned as one email with `type: "work"` and `primary: true`. |
| `active` | `enabled` | Honored by POST, PUT and PATCH. `"True"`/`"False"` strings (as Entra ID sends) are read as booleans. |
| `externalId` | *(not persisted)* | Accepted and ignored. Earlier versions stored it in `federationLink`, the LDAP federation link, which made a SCIM user look LDAP-federated at sign-in. |
| `displayName`, `title`, `preferredLanguage`, `locale`, `timezone`, `nickName`, `phoneNumbers`, `addresses`, the enterprise extension (`department`, `manager`, and so on) and the other User schema attributes | *(not persisted)* | No column on the user record. POST, PUT and PATCH accept them and drop them, so an IdP that sends them on every sync is not refused. `displayName` in responses is built from `"firstName lastName"`; the rest always come back absent. Don't build an IdP attribute mapping that depends on round-tripping these. `phoneNumbers` is never written to the user's SMS MFA number. |
| `password` | *(not persisted)* | Accepted and ignored; SCIM cannot set a password. It is left out of the audit event. |
| `groups` | Read-only, derived from group membership | Not settable on a user (400 `mutability`) |

| SCIM attribute | Idenplane field | Notes |
|---|---|---|
| `displayName` | `name` (and `description`) | Required; must be unique in the realm |
| `members` | Group membership join rows | `value` is the Idenplane user ID; ids that are not users of the realm are skipped |
| `externalId` | *(not persisted)* | Accepted and ignored |

### PATCH

`PATCH /Users/{id}` and `PATCH /Groups/{id}` follow RFC 7644 §3.5.2. The request lists its operations in `Operations` (lowercase `operations` is also read, for older clients). Op names are case-insensitive, so Entra ID's `Add`, `Replace` and `Remove` work. A request is checked in full before anything is written: if one operation is refused, none is applied.

Supported user paths:

| Path | add / replace | remove |
|---|---|---|
| `active` | Sets `enabled` (`true`/`false` or `"True"`/`"False"`) | 400 `invalidValue` |
| `userName` | Sets the username (409 if taken) | 400 `invalidValue` |
| `name.givenName`, `name.familyName` | Sets the name part | Clears it |
| `name` (object value) | Sets the sub-attributes given | Clears both parts |
| `emails`, `emails.value` | Sets the email (primary, or first, of the list) | Clears it |
| `emails[type eq "work"].value`, `emails[primary eq true].value`, `emails[value eq "..."]` | Sets the stored email | Clears it if the filter selects it |
| `emails[type eq "home"]` and other email kinds | Ignored (only one email is stored) | Ignored |
| The unstored attributes listed above, with or without a schema URN prefix | Ignored | Ignored |
| `id`, `meta`, `groups` | 400 `mutability` | 400 `mutability` |
| Anything else | 400 `invalidPath` | 400 `invalidPath` |

An operation without a `path` takes an object `value` whose keys are paths: plain (`active`), dotted (`name.givenName`) or nested (`{"name": {"givenName": "Ada"}}`). A `remove` without a `path` is a 400 `noTarget`. Paths may carry the core schema prefix (`urn:ietf:params:scim:schemas:core:2.0:User:name.givenName`).

Group paths are `displayName` (replace) and `members`:

| Operation | Effect |
|---|---|
| `add`, path `members`, value `[{"value": "<userId>"}]` | Adds the users |
| `replace`, path `members`, value `[...]` | Makes the members exactly these users |
| `remove`, path `members[value eq "<userId>"]` (Okta) | Removes that user |
| `remove`, path `members`, value `[{"value": "<userId>"}]` (Entra ID) | Removes those users |
| `remove`, path `members`, no value | Removes every member |

### Deprovisioning and Sessions

Deactivating a user through SCIM — `PATCH` with `{"op": "Replace", "path": "active", "value": "False"}` (Entra ID), `{"op": "replace", "value": {"active": false}}` (Okta), or `PUT` with `"active": false` — sets `enabled: false` **and signs the user out everywhere**: every session ends and its refresh tokens are revoked, as the admin API's "sign out all sessions" does. Their access tokens stop passing introspection and userinfo at once. Re-activating the user does not bring those tokens back; the user signs in again.

`DELETE /Users/{id}` does **not** hard-delete — it sets `enabled: false` and ends the user's sessions the same way (a soft deprovision). A later `GET` still returns the user, with `active: false`. `DELETE /Groups/{id}` **does** hard-delete the group.

### Filtering

Filters use the RFC 7644 §3.4.2.2 format `attribute operator value`, for example `userName eq "jsmith"`. Supported operators: `eq`, `ne`, `co`, `sw`, `ew`, `gt`, `ge`, `lt`, `le`, and `pr` (present). The value must be one JSON value: a double-quoted string, a number, `true`, `false` or `null`.

- **Only a single condition is supported** — there's no `and`/`or`/grouping. A compound filter is refused with 400 `invalidFilter`.
- **An invalid or unsupported filter is a 400 `invalidFilter`**, never an empty list, so an IdP can't mistake a filter it got wrong for "no such user" and create a duplicate.
- Attribute names are case-insensitive, and string comparisons on `userName`, the name parts and `emails` are case-insensitive (RFC 7643 `caseExact: false`).

Filterable attributes: `userName`, `name.givenName`, `name.familyName`, `emails` / `emails.value`, `active` (`eq`/`ne` with `true`/`false`) and `id` for Users; `displayName` and `id` for Groups. This covers the lookup Okta and Entra ID make before every create (`userName eq "<value>"`) and Entra ID's group lookup (`displayName eq "<value>"`).

### Pagination

`startIndex` is 1-based (values below 1 are read as 1); `count` is capped at 100 per page server-side regardless of what you request (defaults: `startIndex=1`, `count=100`; `count=0` returns only `totalResults`). List and search responses are shaped as:

```json
{
  "schemas": ["urn:ietf:params:scim:api:messages:2.0:ListResponse"],
  "totalResults": 42,
  "startIndex": 1,
  "itemsPerPage": 42,
  "Resources": [ /* ScimUser or ScimGroup objects */ ]
}
```

`excludedAttributes=members` leaves `members` out of group responses.

### Bulk Operations

`POST /Bulk` accepts `{ "schemas": [...], "Operations": [{ method, path, data, bulkId }] }` (lowercase `operations` is also read). `path` is `/Users` or `/Groups` for `POST`, and `/Users/{id}` or `/Groups/{id}` for `PUT`, `PATCH` and `DELETE`; a `PATCH` operation's `data` is a PatchOp body. Each operation runs through the same code as the individual endpoints. The response is a `BulkResponse` whose `Operations` give each operation's `method`, `bulkId`, `status`, `location` and, on failure, the SCIM error as `response`. `failOnErrors` stops processing after that many errors. More than 1000 operations is a 413 `tooMany`. `bulkId` references between operations (`"bulkId:..."`) are not resolved.

## Setting Up

### Admin Console

**SCIM**, under the realm's *Applications* section:

- **SCIM Provisioning** toggle (`scimEnabled`) — must be on, or every `/Users`/`/Groups`/`/Bulk` call returns 401
- **User Autocreate** and **Group Sync** toggles (`scimUserAutocreate`, `scimGroupSyncEnabled`) — stored on the realm and shown on the status view, but not currently read by the user/group provisioning logic; user creation and group membership updates behave the same regardless of these two toggle values today
- **Tokens** — create with a name, optional description, optional expiry date, and optional scopes (see the scopes caveat above); the plaintext token is shown once
- **Attribute Mappings** — a `resourceType`/`scimAttribute`/`idenplaneAttribute`/`direction` table you can populate for your own reference

### Admin API

Token and status management lives under `/admin/realms/{realm}/scim`, protected by the admin API key (this is a *different* credential from the SCIM bearer token itself — use the admin API key to provision SCIM tokens, then hand the SCIM token to your IdP):

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/admin/realms/{realm}/scim/tokens` | Create a token — plaintext shown once |
| `GET` | `/admin/realms/{realm}/scim/tokens` | List tokens (no plaintext) |
| `GET` | `/admin/realms/{realm}/scim/tokens/{tokenId}` | Get one |
| `PUT` | `/admin/realms/{realm}/scim/tokens/{tokenId}/revoke` | Revoke |
| `PUT` | `/admin/realms/{realm}/scim/tokens/{tokenId}/enable` | Enable |
| `PUT` | `/admin/realms/{realm}/scim/tokens/{tokenId}/disable` | Disable |
| `DELETE` | `/admin/realms/{realm}/scim/tokens/{tokenId}` | Delete |
| `GET` | `/admin/realms/{realm}/scim/status` | `enabled`, `userAutocreate`, `groupSyncEnabled`, `activeTokens`, `totalUsers`, `totalGroups` |
| `GET` / `POST` | `/admin/realms/{realm}/scim/attribute-mappings` | List and add entries in the reference mapping table |
| `DELETE` | `/admin/realms/{realm}/scim/attribute-mappings/{mappingId}` | Remove an entry |

```bash
curl -X POST http://localhost:3000/admin/realms/my-realm/scim/tokens \
  -H "x-admin-api-key: $ADMIN_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Okta SCIM",
    "description": "Okta SCIM connector for my-realm"
  }'
```

**Response** (the `token` field is shown once):

```json
{
  "id": "tok_...",
  "name": "Okta SCIM",
  "description": "Okta SCIM connector for my-realm",
  "enabled": true,
  "scopes": ["urn:scim:schemas:core:1.0:Users", "urn:scim:schemas:core:1.0:Groups"],
  "createdAt": "2026-08-02T00:00:00.000Z",
  "expiresAt": null,
  "token": "9kQz...c2"
}
```

### Calling SCIM Directly

```bash
curl "http://localhost:3000/scim/v2/my-realm/Users?filter=userName%20eq%20%22jsmith%22" \
  -H "Authorization: Bearer 9kQz...c2"
```

```bash
curl -X POST http://localhost:3000/scim/v2/my-realm/Users \
  -H "Authorization: Bearer 9kQz...c2" \
  -H "Content-Type: application/json" \
  -d '{
    "userName": "jsmith",
    "name": { "givenName": "Jamie", "familyName": "Smith" },
    "emails": [{ "value": "jsmith@example.com", "primary": true }]
  }'
```

The new user is created enabled unless the request sends `"active": false`. If your IdP's create payload always includes `displayName`, `title`, `preferredLanguage`, `locale`, or `timezone`, that's expected and harmless — see the mapping table above for why those attributes never persist, on this or any other verb.

## Okta Integration Walkthrough

1. In Idenplane, enable **SCIM Provisioning** for the realm (Applications → SCIM), then create a SCIM token (Applications → SCIM → Tokens → Create Token). Copy the plaintext token immediately — it won't be shown again.
2. In Okta, go to **Applications** and create (or edit) a SCIM-capable app integration. Under **Provisioning**, choose **SCIM**.
3. Set the **SCIM connector base URL** to:
   ```
   https://your-idenplane-host/scim/v2/{realmName}
   ```
   substituting your realm's name.
4. Set **Unique identifier field for users** to `userName`.
5. Under **Authentication Mode**, choose **HTTP Header** and paste the SCIM token from step 1 as the bearer token.
6. Click **Test Connector Configuration**. Okta may call the unauthenticated `GET /scim/v2/{realmName}/ServiceProviderConfig` and then an authenticated `GET /scim/v2/{realmName}/Users` with a bearer token — a 401 here almost always means either SCIM isn't enabled for the realm or the token was mistyped.
7. Enable the provisioning actions you want: **Create Users**, **Update User Attributes**, and **Deactivate Users** map directly to `POST /Users`, `PATCH /Users/{id}` (`replace`), and `PATCH` with `{"active": false}`, which disables the user and ends their sessions (see *Deprovisioning and Sessions* above).
8. Assign users/groups to the app in Okta to trigger provisioning. Okta's assignment-check filter is a single `userName eq "<value>"` query, which is within what the filter parser supports.

## Azure AD (Entra ID) Integration Walkthrough

1. In Idenplane, enable SCIM and create a token, same as steps 1 in the Okta walkthrough above.
2. In the Azure portal, open your Enterprise Application and go to **Provisioning** → **Get started** → set **Provisioning Mode** to **Automatic**.
3. Under **Admin Credentials**:
   - **Tenant URL**: `https://your-idenplane-host/scim/v2/{realmName}`
   - **Secret Token**: the SCIM token from step 1
4. Click **Test Connection**. Azure AD calls `GET /scim/v2/{realmName}/Users` (and typically `/ServiceProviderConfig`) with the bearer token to confirm connectivity before saving.
5. Under **Mappings**, review the default **Provision Azure Active Directory Users** attribute mapping. Azure AD's default mapping expects `userName`, `active`, `emails[type eq "work"].value`, `name.givenName`, and `name.familyName` — all of which line up with the field mapping table above. Entra ID also sends `displayName`, `title`, `externalId`, phone numbers, addresses and enterprise attributes such as `department`; Idenplane accepts and ignores them (see the mapping table). Keep **Matching precedence** on `userName`: `externalId` is not stored, so it cannot be used to match. Deactivation arrives as `{"op": "Replace", "path": "active", "value": "False"}` and signs the user out everywhere.
6. Set **Scope** to assigned users and groups (or "All Users", depending on your directory size), then turn **Provisioning Status** to **On**.
7. Azure AD polls periodically (its own schedule, not something Idenplane controls) rather than provisioning instantly on assignment — use **Provision on demand** in the Azure portal to test a single user without waiting for the next cycle.
