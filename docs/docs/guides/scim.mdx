# SCIM 2.0 Provisioning

Idenplane implements the SCIM 2.0 protocol (RFC 7644) so an external identity provider — Okta, Azure AD (Entra ID), or anything else that speaks SCIM — can create, update, and deprovision users and groups directly, instead of you syncing them by hand.

---

## Concepts

### Base URL and Endpoints

The SCIM base path for a realm is:

```
/scim/v2/{realmName}
```

where `{realmName}` is the realm's `name` (not its UUID). The implemented resource endpoints, all under that base path:

| Method | Path | Purpose |
|---|---|---|
| `GET` / `POST` | `/Users` | List (with filter/pagination) / create |
| `GET` / `PUT` / `PATCH` / `DELETE` | `/Users/{id}` | Get / full replace / partial update / deprovision |
| `POST` | `/Users/.search` | Search via POST body instead of query string |
| `GET` / `POST` | `/Groups` | List (with filter/pagination) / create |
| `GET` / `PUT` / `PATCH` / `DELETE` | `/Groups/{id}` | Get / full replace / partial update / delete |
| `POST` | `/Groups/.search` | Search via POST body |
| `POST` | `/Bulk` | Batch of the operations above in one request |

Three discovery endpoints sit one level up, at `/scim/v2/...` with **no realm segment and no authentication**: `GET /scim/v2/ServiceProviderConfig`, `GET /scim/v2/Schemas` (and `/Schemas/{id}`), and `GET /scim/v2/ResourceTypes` (and `/ResourceTypes/{name}`). These describe the server's capabilities and are what an IdP's "test connection" step typically hits first.

### Authentication

Every `/Users`, `/Groups`, and `/Bulk` call requires `Authorization: Bearer <token>`. The token is opaque — generated by Idenplane, not a JWT — and validated by hashing the presented value with SHA-256 and comparing it against the stored hash; the plaintext is never stored and is shown to you exactly once, at creation time.

If the realm's SCIM provisioning is turned off, or the bearer token is missing, unknown, revoked, expired, disabled, or issued for a different realm, every one of those endpoints returns **401 Unauthorized** (not 403 — despite what the admin console's toggle description says).

Tokens carry `scopes` (defaulting to `["urn:scim:schemas:core:1.0:Users", "urn:scim:schemas:core:1.0:Groups"]` if you don't specify any) and an optional `expiresAt`. As of today, `scopes` are stored and returned but not read anywhere in the authorization check — they're a label for your own bookkeeping, not an access-control boundary. Every valid token can call every SCIM endpoint in its realm regardless of its `scopes` value.

### Schema URNs

Resources are tagged with SCIM **1.0**-style schema URNs — `urn:scim:schemas:core:1.0:User`, `:Group`, `:ListResponse`, `:ServiceProviderConfig` — rather than the RFC 7643 2.0 URNs (`urn:ietf:params:scim:schemas:core:2.0:User`) that a strict SCIM 2.0 client might expect. The endpoint shapes, status codes, filtering, and PATCH semantics otherwise follow RFC 7644. Most IdPs tolerate this, but if you're debugging an IdP-side schema validation error, this is the first thing to check.

### User and Group Field Mapping

| SCIM attribute | Idenplane field | Notes |
|---|---|---|
| `userName` | `username` | Required; must be unique in the realm |
| `name.givenName` | `firstName` | |
| `name.familyName` | `lastName` | |
| `emails` (primary, or first if none marked primary) | `email` | Must be unique in the realm |
| `externalId` | `federationLink` | |
| `active` | `enabled` | Honored by PUT and PATCH. **Ignored by POST** — a newly created user is enabled by the database default regardless of what `active` you send. |
| `displayName`, `title`, `preferredLanguage`, `locale`, `timezone` | *(not persisted)* | **None of these have a backing database column on the user record today.** POST and PUT silently drop them — the value is accepted, parsed, and discarded with no error. PATCH tries to write them through the same generic update path used for real fields, which is more likely to surface as a hard error on that request than to succeed, since the underlying data layer rejects unrecognized columns. Either way, nothing is stored: `displayName` in every read response is synthesized from `"firstName lastName"`, and `title`/`preferredLanguage`/`locale`/`timezone` always come back absent. Don't build an IdP attribute mapping that depends on round-tripping these. |
| `groups` | Read-only, derived from group membership | Not settable on a user |

| SCIM attribute | Idenplane field | Notes |
|---|---|---|
| `displayName` | `name` (and `description`) | Required; must be unique in the realm |
| `members` | Group membership join rows | `value` is the Idenplane user ID |
| `externalId` | Echoed back as the group's own ID | Not stored separately |

### Deprovisioning Is Asymmetric

`DELETE /Users/{id}` does **not** hard-delete — it sets `enabled: false` (a soft deprovision, consistent with how most IdPs expect user deletion to behave). `DELETE /Groups/{id}` **does** hard-delete the group. If your IdP's "deactivate on unassign" behavior sends `PATCH .../Users/{id}` with a `replace` of `{ "active": false }`, that also works and maps to the same `enabled: false` update. A PATCH `remove` operation on a user, however, is currently a no-op — it's accepted and logged but doesn't change any field; use `replace` (or the DELETE endpoint) to deprovision. PATCH `remove` on a *group* does work for removing a specific member, via a path like `members[value eq '<userId>']`.

### Filtering

Filters use the RFC 7644 §3.4.2.2 format `attribute operator value`, for example `userName eq "jsmith"`. Supported operators: `eq`, `ne`, `co`, `sw`, `ew`, `gt`, `ge`, `lt`, `le`.

Two important limits to design your IdP-side assignment rules around:

- **Only a single condition is supported** — there's no `and`/`or`/grouping. A compound filter like `userName eq "jsmith" and active eq true` will parse but produce an incorrect result rather than an error, because the parser treats everything after the operator as the value. Stick to one condition per filter.
- **An invalid or unsupported filter returns an empty result, not a 400.** If `/Users?filter=...` can't be parsed (or references an attribute the filter parser doesn't recognize for that resource), the response is a valid `ListResponse` with `totalResults: 0` — indistinguishable, from the caller's side, from "no matches." If an IdP reports zero users found and you expected some, double-check the filter syntax before assuming the data is wrong.

Filterable attributes are limited to what the mapping table above supports for `eq`/`ne`/`co`/`sw`/`ew`/`gt`/`ge`/`lt`/`le`: `userName`, `name.givenName`, `name.familyName`, `displayName`, `emails.value`, `active`, `title`, and `externalId` for Users; `displayName` (any operator) and `externalId` (`eq` only) for Groups. This covers the lookup Okta and Azure AD actually perform during assignment (typically `userName eq "<value>"`).

### Pagination

`startIndex` is 1-based; `count` is capped at 100 per page server-side regardless of what you request (defaults: `startIndex=1`, `count=100`). List and search responses are shaped as:

```json
{
  "schemas": ["urn:scim:schemas:core:1.0:ListResponse"],
  "totalResults": 42,
  "startIndex": 1,
  "itemsPerPage": 42,
  "Resources": [ /* ScimUser or ScimGroup objects */ ]
}
```

### Bulk Operations

`POST /Bulk` accepts a list of `{ method, path, data, bulkId }` operations (`path` is `/Users` or `/Users/{id}`, `/Groups` or `/Groups/{id}`) and applies each one through the same user/group service methods as the individual endpoints, returning a `bulkResponse` with a per-operation status. The service-provider config advertises `bulk.supported: true` with a 1000-operation and 10 MB payload cap.

## Setting Up

### Admin Console

**SCIM**, under the realm's *Applications* section:

- **SCIM Provisioning** toggle (`scimEnabled`) — must be on, or every `/Users`/`/Groups`/`/Bulk` call returns 401
- **User Autocreate** and **Group Sync** toggles (`scimUserAutocreate`, `scimGroupSyncEnabled`) — stored on the realm and shown on the status view, but not currently read by the user/group provisioning logic; user creation and group membership updates behave the same regardless of these two toggle values today
- **Tokens** — create with a name, optional description, optional expiry date, and optional scopes (see the scopes caveat above); the plaintext token is shown once
- **Attribute Mappings** — a `resourceType`/`scimAttribute`/`idenplaneAttribute`/`direction` table you can populate for your own reference

### Admin API

Token and status management lives under `/admin/realms/{realm}/scim`, protected by the admin API key (this is a *different* credential from the SCIM bearer token itself — use the admin API key to provision SCIM tokens, then hand the SCIM token to your IdP):

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/admin/realms/{realm}/scim/tokens` | Create a token — plaintext shown once |
| `GET` | `/admin/realms/{realm}/scim/tokens` | List tokens (no plaintext) |
| `GET` | `/admin/realms/{realm}/scim/tokens/{tokenId}` | Get one |
| `PUT` | `/admin/realms/{realm}/scim/tokens/{tokenId}/revoke` | Revoke |
| `PUT` | `/admin/realms/{realm}/scim/tokens/{tokenId}/enable` | Enable |
| `PUT` | `/admin/realms/{realm}/scim/tokens/{tokenId}/disable` | Disable |
| `DELETE` | `/admin/realms/{realm}/scim/tokens/{tokenId}` | Delete |
| `GET` | `/admin/realms/{realm}/scim/status` | `enabled`, `userAutocreate`, `groupSyncEnabled`, `activeTokens`, `totalUsers`, `totalGroups` |
| `GET` / `POST` / `DELETE` | `/admin/realms/{realm}/scim/attribute-mappings` | Manage the reference mapping table |

```bash
curl -X POST http://localhost:3000/admin/realms/my-realm/scim/tokens \
  -H "x-admin-api-key: $ADMIN_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Okta SCIM",
    "description": "Okta SCIM connector for my-realm"
  }'
```

**Response** (the `token` field is shown once):

```json
{
  "id": "tok_...",
  "name": "Okta SCIM",
  "description": "Okta SCIM connector for my-realm",
  "enabled": true,
  "scopes": ["urn:scim:schemas:core:1.0:Users", "urn:scim:schemas:core:1.0:Groups"],
  "createdAt": "2026-08-02T00:00:00.000Z",
  "expiresAt": null,
  "token": "9kQz...c2"
}
```

### Calling SCIM Directly

```bash
curl "http://localhost:3000/scim/v2/my-realm/Users?filter=userName%20eq%20%22jsmith%22" \
  -H "Authorization: Bearer 9kQz...c2"
```

```bash
curl -X POST http://localhost:3000/scim/v2/my-realm/Users \
  -H "Authorization: Bearer 9kQz...c2" \
  -H "Content-Type: application/json" \
  -d '{
    "userName": "jsmith",
    "name": { "givenName": "Jamie", "familyName": "Smith" },
    "emails": [{ "value": "jsmith@example.com", "primary": true }]
  }'
```

The new user is created enabled by default — `active` isn't read on create (see the mapping table above). If your IdP's create payload always includes `displayName`, `title`, `preferredLanguage`, `locale`, or `timezone`, that's expected and harmless — see the mapping table above for why those attributes never persist, on this or any other verb.

## Okta Integration Walkthrough

1. In Idenplane, enable **SCIM Provisioning** for the realm (Applications → SCIM), then create a SCIM token (Applications → SCIM → Tokens → Create Token). Copy the plaintext token immediately — it won't be shown again.
2. In Okta, go to **Applications** and create (or edit) a SCIM-capable app integration. Under **Provisioning**, choose **SCIM**.
3. Set the **SCIM connector base URL** to:
   ```
   https://your-idenplane-host/scim/v2/{realmName}
   ```
   substituting your realm's name.
4. Set **Unique identifier field for users** to `userName`.
5. Under **Authentication Mode**, choose **HTTP Header** and paste the SCIM token from step 1 as the bearer token.
6. Click **Test Connector Configuration**. Okta will call the unauthenticated `GET /scim/v2/ServiceProviderConfig` and then an authenticated `GET /scim/v2/{realmName}/Users` with a bearer token — a 401 here almost always means either SCIM isn't enabled for the realm or the token was mistyped.
7. Enable the provisioning actions you want: **Create Users**, **Update User Attributes**, and **Deactivate Users** map directly to `POST /Users`, `PATCH /Users/{id}` (`replace`), and the deactivate-on-unassign behavior described above (`active: false`, which Idenplane maps to `enabled: false`).
8. Assign users/groups to the app in Okta to trigger provisioning. Okta's assignment-check filter is a single `userName eq "<value>"` query, which is within what the filter parser supports.

## Azure AD (Entra ID) Integration Walkthrough

1. In Idenplane, enable SCIM and create a token, same as steps 1 in the Okta walkthrough above.
2. In the Azure portal, open your Enterprise Application and go to **Provisioning** → **Get started** → set **Provisioning Mode** to **Automatic**.
3. Under **Admin Credentials**:
   - **Tenant URL**: `https://your-idenplane-host/scim/v2/{realmName}`
   - **Secret Token**: the SCIM token from step 1
4. Click **Test Connection**. Azure AD calls `GET /scim/v2/{realmName}/Users` (and typically `/ServiceProviderConfig`) with the bearer token to confirm connectivity before saving.
5. Under **Mappings**, review the default **Provision Azure Active Directory Users** attribute mapping. Azure AD's default mapping expects `userName`, `active`, `emails[type eq "work"].value`, `name.givenName`, and `name.familyName` — all of which line up with the field mapping table above. Leave `externalId` mapped to Azure AD's `objectId`; it round-trips to `federationLink` on the Idenplane side.
6. Set **Scope** to assigned users and groups (or "All Users", depending on your directory size), then turn **Provisioning Status** to **On**.
7. Azure AD polls periodically (its own schedule, not something Idenplane controls) rather than provisioning instantly on assignment — use **Provision on demand** in the Azure portal to test a single user without waiting for the next cycle.
