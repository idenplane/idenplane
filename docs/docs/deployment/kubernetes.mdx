# Kubernetes Deployment

Idenplane provides a Helm chart for production-grade Kubernetes deployments. This guide covers installation, configuration, and common operational tasks.

---

## Prerequisites

| Requirement | Version |
|-------------|---------|
| Kubernetes | 1.24+ |
| Helm | 3.12+ |
| kubectl | 1.24+ |

---

## Quick Start

The fastest way to deploy Idenplane on Kubernetes:

```bash
# Add the Idenplane Helm repository (if published)
helm repo add idenplane https://charts.idenplane.com
helm repo update

# Or install from local chart
helm repo add file://./helm/idenplane

# Create namespace
kubectl create namespace idenplane

# Install with production values
helm upgrade --install idenplane ./helm/idenplane \
  --namespace idenplane \
  --values ./helm/idenplane/values.production.yaml \
  --set env.BASE_URL="https://auth.example.com"

# Read the generated admin password
kubectl get secret --namespace idenplane idenplane-keys \
  -o jsonpath="{.data.ADMIN_PASSWORD}" | base64 -d; echo
```

The chart generates the admin password, the admin API key, the webhook encryption keys and the bundled database password on the first install, and keeps them on upgrades. See [Secrets](#2-secrets).

## Installing from Local Chart

### 1. Prepare Values File

Create a `production-values.yaml` file:

```yaml
# replica count
replicaCount: 3

# image
image:
  repository: islamawad/idenplane
  tag: "latest"
  pullPolicy: IfNotPresent

# ingress
ingress:
  enabled: true
  className: nginx
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod
    nginx.ingress.kubernetes.io/proxy-body-size: "10m"
  hosts:
    - host: auth.example.com
      paths:
        - path: /
          pathType: Prefix
  tls:
    - secretName: idenplane-tls
      hosts:
        - auth.example.com

# environment
env:
  NODE_ENV: "production"
  BASE_URL: "https://auth.example.com"
  SESSION_STORE: "database"
  THROTTLE_TTL: "60000"
  THROTTLE_LIMIT: "100"

# secrets — leave empty to generate on first install (see Secrets below)
secrets:
  existingSecret: ""   # required with Argo CD / Flux / helm template
  DATABASE_URL: ""     # required when postgresql.enabled is false

# bundled PostgreSQL (official image); prefer a managed database in production
postgresql:
  enabled: true
  auth:
    username: idenplane
    password: ""       # generated when empty
    database: idenplane
  primary:
    persistence:
      enabled: true
      size: 20Gi

# horizontal pod autoscaler
autoscaling:
  enabled: true
  minReplicas: 2
  maxReplicas: 10
  targetCPUUtilizationPercentage: 70

# pod disruption budget
podDisruptionBudget:
  enabled: true
  maxUnavailable: 1

# high availability — spread pods across nodes
affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchLabels:
              app.kubernetes.io/name: idenplane
          topologyKey: kubernetes.io/hostname
```

### 2. Secrets

The chart keeps the application keys in the `<release>-idenplane-keys` Secret: `ADMIN_API_KEY`, `ADMIN_PASSWORD` (the initial `admin` user), `WEBHOOK_SECRET_KEY` and `WEBHOOK_ENCRYPTION_SALT`. A value you set under `secrets:` is used as is. An empty one is generated on the first install and read back from the cluster on every upgrade, so it never changes. The Secret has `helm.sh/resource-policy: keep`, so `helm uninstall` leaves it in place.

Back the Secret up. The two webhook values encrypt stored webhook secrets, and losing them makes those secrets unreadable.

:::warning GitOps
Argo CD, Flux and `helm template` cannot read the stored Secret back, so they would generate new keys on every render. Create the four keys yourself and point the chart at them:

```bash
kubectl create secret generic idenplane-app-keys --namespace idenplane \
  --from-literal=ADMIN_API_KEY="$(openssl rand -hex 32)" \
  --from-literal=ADMIN_PASSWORD="$(openssl rand -hex 16)" \
  --from-literal=WEBHOOK_SECRET_KEY="$(openssl rand -hex 32)" \
  --from-literal=WEBHOOK_ENCRYPTION_SALT="$(openssl rand -hex 16)"
```

Then set `secrets.existingSecret: idenplane-app-keys`, and likewise `postgresql.auth.existingSecret` (key `password`) for the bundled database.
:::

To [rotate the encryption key](production.md#rotating-the-encryption-key), set the new values as `secrets.WEBHOOK_SECRET_KEY` / `secrets.WEBHOOK_ENCRYPTION_SALT` and the old ones as `secrets.WEBHOOK_SECRET_KEY_PREVIOUS` / `secrets.WEBHOOK_ENCRYPTION_SALT_PREVIOUS` (with `secrets.existingSecret`, add those two keys to your Secret instead). The chart never generates the previous key. Once the log reports `Key rotation complete`, remove the previous values and upgrade again. Keep the new ones set explicitly, or leave them empty: the Secret now holds the new values, and the chart keeps them.

Rendering fails on the old placeholders (`change-me-in-production`, `REPLACE_WITH_STRONG_SECRET`, `REPLACE_WITH_STRONG_DB_PASSWORD`), on an admin API key shorter than 32 characters and on an admin password shorter than 12.

### 3. Install the Chart

```bash
helm upgrade --install idenplane ./helm/idenplane \
  --namespace idenplane \
  --create-namespace \
  --values ./helm/idenplane/values.production.yaml \
  --set env.BASE_URL="https://auth.example.com"
```

## Configuration Reference

### Image Settings

| Parameter | Description | Default |
|-----------|-------------|---------|
| `image.repository` | Container image repository | `islamawad/idenplane` |
| `image.tag` | Image tag (defaults to chart appVersion) | `""` |
| `image.pullPolicy` | Image pull policy | `IfNotPresent` |
| `imagePullSecrets` | Secrets for private registries | `[]` |

### Service Configuration

| Parameter | Description | Default |
|-----------|-------------|---------|
| `service.type` | Kubernetes Service type | `ClusterIP` |
| `service.port` | Service port | `3000` |
| `service.targetPort` | Container port | Same as `service.port` |

### Ingress Configuration

| Parameter | Description | Default |
|-----------|-------------|---------|
| `ingress.enabled` | Enable Ingress | `false` |
| `ingress.className` | Ingress class (nginx, traefik) | `""` |
| `ingress.annotations` | Custom annotations | `{}` |
| `ingress.hosts` | Host configurations | See values.yaml |
| `ingress.tls` | TLS configurations | `[]` |

Example ingress annotations for cert-manager:

```yaml
ingress:
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod
    kubernetes.io/ingress.class: nginx
```

### Resource Limits

| Parameter | Request | Limit |
|-----------|---------|-------|
| CPU | 100m | 500m |
| Memory | 128Mi | 512Mi |

For production, increase resources:

```yaml
resources:
  requests:
    cpu: 250m
    memory: 256Mi
  limits:
    cpu: 500m
    memory: 512Mi
```

### Probe Configuration

| Probe | Path | Initial Delay | Period |
|-------|------|--------------|--------|
| Startup | `/health` | 10s | 10s |
| Liveness | `/health` | 15s | 20s |
| Readiness | `/health/ready` | 10s | 10s |

## Database Configuration

### Bundled PostgreSQL (Default)

The chart runs one PostgreSQL pod on the official `postgres` image, which suits evaluation and small installs. Its password is generated unless you set `postgresql.auth.password` or `postgresql.auth.existingSecret`. For production, prefer a managed database (below).

```yaml
postgresql:
  enabled: true
  image:
    tag: "17-bookworm"
  primary:
    persistence:
      enabled: true
      size: 20Gi
```

#### Upgrading from chart 0.2.x (Bitnami sub-chart)

Chart 0.2.x pulled PostgreSQL and Redis from Bitnami sub-charts. Their `docker.io/bitnami` images are no longer published, so those pods cannot be rescheduled. Chart 0.3.0 replaces them with the official images and reuses the existing volume: same claim name (`data-<release>-postgresql-0`), same data directory, the same user ID (1001) and the same PostgreSQL major version (17, Debian).

A StatefulSet's selector cannot change, so delete the old StatefulSets without deleting their volumes, then upgrade:

```bash
kubectl delete statefulset idenplane-postgresql --namespace idenplane --cascade=orphan
kubectl delete statefulset idenplane-redis-master --namespace idenplane --cascade=orphan  # only if redis.enabled
helm upgrade idenplane ./helm/idenplane --namespace idenplane --reuse-values
```

Take a `pg_dump` first. The database password stays the same: the chart reads it from the existing `<release>-postgresql` Secret.

### External PostgreSQL

To use an external database:

```yaml
postgresql:
  enabled: false

secrets:
  DATABASE_URL: "postgresql://user:pass@host:5432/idenplane"
```

### Redis (Optional)

Enable Redis for session caching and improved performance:

```yaml
redis:
  enabled: true
  auth:
    enabled: true
    password: ""   # generated when empty

env:
  SESSION_STORE: "redis"   # REDIS_URL is wired to the bundled Redis
```

## High Availability

### Horizontal Pod Autoscaler

Enable HPA for automatic scaling:

```yaml
autoscaling:
  enabled: true
  minReplicas: 2
  maxReplicas: 10
  targetCPUUtilizationPercentage: 70
```

### Pod Disruption Budget

Ensure availability during node maintenance:

```yaml
podDisruptionBudget:
  enabled: true
  maxUnavailable: 1
```

### Pod Anti-Affinity

Spread pods across nodes:

```yaml
affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchLabels:
              app.kubernetes.io/name: idenplane
          topologyKey: kubernetes.io/hostname
```

## Security Configuration

### Pod Security Context

```yaml
podSecurityContext:
  fsGroup: 1000
  runAsNonRoot: true
  runAsUser: 1000
```

### Container Security Context

```yaml
securityContext:
  allowPrivilegeEscalation: false
  capabilities:
    drop:
      - ALL
  readOnlyRootFilesystem: false
  runAsNonRoot: true
  runAsUser: 1000
```

### Network Policies

Add a NetworkPolicy to restrict traffic:

```yaml
# network-policy.yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: idenplane-network-policy
  namespace: idenplane
spec:
  podSelector:
    matchLabels:
      app.kubernetes.io/name: idenplane
  policyTypes:
    - Ingress
    - Egress
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              name: ingress-nginx
      ports:
        - protocol: TCP
          port: 3000
  egress:
    - to:
        - podSelector:
            matchLabels:
              app.kubernetes.io/name: postgresql
      ports:
        - protocol: TCP
          port: 5432
```

## Managing Deployments

### Upgrading

```bash
# Upgrade to new version
helm upgrade idenplane ./helm/idenplane \
  --namespace idenplane \
  --values ./helm/idenplane/values.production.yaml

# Upgrade with new values
helm upgrade idenplane ./helm/idenplane \
  --namespace idenplane \
  --set image.tag="1.2.3"
```

### Rolling Back

```bash
# List release history
helm history idenplane --namespace idenplane

# Roll back to previous revision
helm rollback idenplane --namespace idenplane

# Roll back to specific revision
helm rollback idenplane --revision 3 --namespace idenplane
```

### Uninstalling

```bash
# Remove the release (preserves data with PVCs)
helm uninstall idenplane --namespace idenplane

# Remove with PVCs (deletes data!)
helm uninstall idenplane --namespace idenplane
kubectl delete pvc -n idenplane -l app.kubernetes.io/name=idenplane
```

## Monitoring

### Health Endpoints

| Endpoint | Description |
|----------|-------------|
| `/health` | Liveness check |
| `/health/ready` | Readiness check |

### Viewing Logs

```bash
# Follow pod logs
kubectl logs -n idenplane -l app.kubernetes.io/name=idenplane -f

# View previous container logs
kubectl logs -n idenplane -l app.kubernetes.io/name=idenplane --previous
```

### Checking Status

```bash
# Helm release status
helm status idenplane --namespace idenplane

# Pod status
kubectl get pods -n idenplane

# Service status
kubectl get svc -n idenplane

# Ingress status
kubectl get ingress -n idenplane
```

### Common Commands

```bash
# Describe deployment
kubectl describe deployment idenplane -n idenplane

# Describe pod
kubectl describe pod -n idenplane -l app.kubernetes.io/name=idenplane

# Execute shell in pod
kubectl exec -it -n idenplane deploy/idenplane -- sh

# Port forward for local access
kubectl port-forward -n idenplane svc/idenplane 3000:3000
```

## Troubleshooting

### Pod Not Starting

1. Check pod status:
   ```bash
   kubectl get pods -n idenplane
   kubectl describe pod -n idenplane <pod-name>
   ```

2. Check container logs:
   ```bash
   kubectl logs -n idenplane <pod-name>
   ```

3. Verify secrets exist:
   ```bash
   kubectl get secret -n idenplane
   ```

### ImagePullBackOff

1. Verify image exists:
   ```bash
   kubectl describe pod -n idenplane <pod-name>
   ```

2. Check image pull secret if using private registry:
   ```bash
   kubectl create secret docker-registry regcred \
     --docker-server=https://index.docker.io/v1/ \
     --docker-username=<user> \
     --docker-password=<token> \
     --docker-email=<email> \
     --namespace idenplane
   ```

### Database Connection Issues

1. Verify PostgreSQL is running:
   ```bash
   kubectl get pods -n idenplane -l app.kubernetes.io/name=postgresql
   ```

2. Check connection string:
   ```bash
   kubectl exec -it -n idenplane deploy/idenplane -- sh -c 'echo $DATABASE_URL'
   ```

3. Test connectivity:
   ```bash
   kubectl exec -it -n idenplane deploy/idenplane -- nc -zv postgresql 5432
   ```
